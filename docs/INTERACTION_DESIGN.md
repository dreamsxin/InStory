# InStory 交互设计说明

版本：v1.1  
日期：2026-09-06  
状态：MVP 交互基线；第 11–13 章记录已实现的实际流程与待补齐项

本文档定义 InStory MVP 阶段的客户端交互模型。产品核心不再是“每一步都要求用户选择”，而是“阅读为主，入戏为触发”：用户默认连续阅读，在关键时刻或主动点击按钮时进入故事世界参与行动。

第 1–10 章是设计基线（意图与原则）。第 11 章之后描述当前代码里真实存在的路由、控件和流程，以及尚未补齐的部分；两者不一致时，以第 11 章之后为现状。

## 1. 设计原则

- 阅读优先：用户应先获得小说式连续阅读体验，不被频繁选择打断。
- 随时入戏：用户可以在任意阅读位置点击“入戏”接管当前场景。
- 关键介入：系统在危机、询问、线索、路线分歧和章节转折处提示可参与。
- 角色即上下文：“我的角色”不是装饰资料，而是 AI 生成互动时的身份设定。
- 创作轻量化：MVP 只提供必要的故事世界和角色配置，不做复杂工作流。
- 移动端优先：参考 AI 角色聊天产品的移动端布局，但保持 InStory 的阅读叙事定位。

## 2. 主信息架构

MVP 客户端保留三个核心入口：

1. 故事
   - 浏览可进入的故事。
   - 这是探索入口，面向所有已可进入的作品，不承担“我的作品管理”。
   - 展示题材、简介、AI 自由度、世界状态。
   - 进入前选择“我的角色”。

2. 继续阅读
   - 展示最近会话。
   - 快速回到上次阅读位置。
   - 显示当前故事、当前角色、最近关键节点。

3. 创作
   - 普通用户的创作控制台。
   - 分为 `角色库` 和 `故事工作台` 两层。
   - 角色库展示和创建“我的角色”。
   - 故事工作台展示和创建“我的故事”，管理世界观、起点场景、故事演员、剧情锚点。
   - 创建故事时只能选择自己创建的角色作为故事演员。
   - 选择入戏体验模式：剧本入戏、共演入戏、即兴入戏。
   - MVP 阶段保持表单化，不做复杂可视化编排。

移动端可使用底部 Tab：`故事`、`继续`、`创作`。桌面端可使用顶部导航。`角色` 不作为独立主导航，也不做独立角色聊天入口；角色对话应发生在用户进入故事后的入戏场景里。

## 3. 首页布局

首页应同时回答三个问题：

- 我能进入哪个世界？
- 我准备用哪个角色进入？
- 我上次读到哪里？

推荐结构：

```text
Header
  Brand
  当前角色快捷入口

Main
  继续阅读
  故事世界列表
  我的角色快捷区

Create Entry
  创建角色
  创建故事世界
```

参考项目的可借鉴模式：

- 用 Feed 或卡片列表承载内容发现。
- 用底部弹层或浮层承载创建入口。
- 用头像、标签和短描述快速表达角色身份。
- 在核心页面保留当前身份入口。

不照搬的部分：

- 不把产品变成纯聊天列表。
- 不把图片生成、群聊、直播等复杂能力放入 MVP。
- 不用强装饰卡片压过阅读正文。

## 4. 我的角色

### 4.1 角色列表

角色卡片展示：

- 头像或默认形象
- 名称
- 性别
- 性格摘要
- 身份背景摘要
- 最近使用故事

主要操作：

- 新建角色
- 编辑角色
- 删除角色
- 设为默认入戏角色
- 进入故事时选择

### 4.2 创建角色

这里的“角色”指读者自己的入戏身份，不是作者在故事里创建的 NPC 或原生角色。它的作用是告诉 AI：读者以什么名字、性格、背景和行为倾向进入故事。

MVP 表单字段：

- 名称：用户在故事中的名字。
- 性别：可选，允许用户自由填写或选择“不设定”。
- 性格：给 AI 使用的行为倾向。
- 头像或形象 URL：MVP 可先用 URL 或默认头像。
- 身份背景：用户是谁，来自哪里，有什么能力或限制。
- AI 互动描述：补充说明 AI 在故事中应如何理解该角色。

入戏角色一律仅自己可见，表单里没有可见性选项。此前有一个 `公开可展示` 开关，但没有任何地方能浏览别人的角色、作者也不能把别人的角色选进故事，两个选项对用户完全等价——不生效的开关等于界面在替一个不存在的功能许诺，已经撤掉。若日后真做「公开角色可被作者选入故事」，那是一次产品决定（需要浏览入口、选角授权语义、原主还能不能改），届时连同入口一起加回来。


表单提示应强调“这些内容会影响 AI 如何写你”，避免用户误以为只是个人资料。

MVP 中角色管理位于 `创作 -> 角色库`。独立 `角色` 导航暂不保留，避免把 InStory 误导成普通 AI 角色聊天产品。后续若增加“角色探索”，也应作为从角色进入故事的发现入口，而不是脱离故事的聊天大厅。

### 4.3 角色选择

进入故事前弹出角色选择：

```text
进入《雨夜旧宅》

选择你的入戏身份
  林向晚
  沈既白
  新建角色

按钮
  以此角色进入
```

如果用户没有角色：

- 展示快速创建表单。
- 允许使用默认“陌生来客”先进入。

## 5. 阅读器

阅读器包含两种状态：阅读模式和入戏模式。

### 5.1 阅读模式

默认状态。用户像看小说一样连续阅读。

页面结构：

```text
顶部
  返回
  故事标题
  当前角色胶囊

正文
  连续段落
  NPC 对话
  场景变化
  关键线索提示

悬浮操作
  继续阅读
  入戏行动
  状态
  记忆
```

阅读模式不强制用户每段都选择。AI 可生成多个自然段或一个小节，并在适合的位置附带介入节点。

MVP 当前实现采用“阅读优先工具坞”：

- `继续阅读` 是主操作，按当前角色倾向自然推进下一小节。
- `入戏行动` 是次操作，展开行动面板后再显示建议行动和自由输入。
- `状态` 和 `记忆` 不常驻占屏，只通过浮动工具坞按需展开。
- `沉浸阅读` 收起信息栏只留正文；工具坞常驻，所以出口和信息栏随时能召回。
- 顶栏最左是 `← 书架`：阅读页必须有一条离开的路，不能只靠浏览器后退。
- 正文按窗口加载，更早的回合用 `载入更早的回合` 取回；换地点时插入场景分隔。
- 每个故事可配置阅读装帧（经典书页 / 西方幻想 / 东方水墨 / 哥特悬疑 / 赛博未来），边框画在滚动窗口上，正文在框内滚动。
- 手机竖屏下工具坞固定在底部安全区上方，面板从底部浮出；手机横屏下工具坞靠右上，面板靠右侧浮出，避免遮挡正文阅读区。

### 5.2 入戏按钮

按钮目标：让用户随时接管当前场景。

移动端位置：

- 右下角悬浮按钮。
- 避开输入法和系统安全区。

桌面端位置：

- 阅读区右侧。
- 或底部工具栏。

文案可根据上下文变化：

- 入戏
- 接管这一幕
- 我要行动
- 和角色对话
- 改变剧情

### 5.3 关键介入节点

系统可在以下场景生成介入提示：

- NPC 向用户发问。
- 用户发现线索。
- 危机逼近。
- 路线出现分歧。
- 角色关系出现变化。
- 章节进入转折点。

提示样式应低打扰：

```text
陆清河停下脚步，回头看你。

你可以继续阅读，也可以入戏改变这一幕。

[继续阅读] [入戏参与]
```

如果用户选择继续阅读，AI 应按当前角色默认倾向推进，不应强制等待。

实现现状：生成结果里带 `intervention`（`kind` 取上面六种之一，`prompt` 是一句故事口吻的提示），随回合存库。模型不标时，服务端按这一段真实改变的状态补一个，所以这件事不依赖模型的自觉。阅读器把它显示在那一段正文下面，只有最新一段带 `入戏参与`；`继续阅读` 沿用正文下方的常驻按钮，不在提示里重复。普通推进段落 `intervention` 为空，界面上什么都不多出来。

### 5.4 入戏模式

触发方式：

- 点击常驻“入戏”按钮。
- 点击关键节点的“入戏参与”。
- 点击某个系统建议行动。

入戏面板内容：

- 当前角色
- 当前场景
- 可选行动建议
- 自由输入框
- 提交按钮

行动类型：

- 说一句话
- 做一个动作
- 观察环境
- 使用物品
- 更换角色，MVP 可先不支持会话中更换

提交后：

- 服务端生成入戏结果。
- 更新世界状态、关系、线索、记忆。
- 将结果写回正文。
- 回到阅读模式。

### 5.5 交互与叙事边界

“每一步都要选择”不是 InStory 的目标体验。若阅读器频繁停在选项列表，通常同时说明两个问题：

- 交互设计问题：把选项放在主阅读流中，会把小说阅读变成问答式流程。
- 叙事模型问题：故事世界、剧情锚点和生成协议还没有支持段落式推进与关键节点判断。

因此 MVP 的落地策略是先在 UI 上把选择降级为“介入建议”，再在服务端逐步拆分 `read_segment` 与 `intervention_turn`。用户不操作时，故事也必须能够自然推进；用户主动介入时，AI 才读取角色设定、当前状态和建议行动生成互动结果。

阅读模式的内容长度应由作品配置驱动。作者可以设置默认推进长度，系统据此生成一个完整阅读小节；如果作者已经为当前选择配置了后续正文，应优先展示作者预设，再由 AI 做局部个性化补写。

UI 层不能假设 HeroUI 会自动完成阅读器自适应。HeroUI 适合承载按钮、卡片、表单、选择器和弹层等组件；阅读器的 App Shell、横竖屏布局、安全区、正文宽度、文本断行和工具坞位置必须由 InStory 自己定义。

## 6. 继续阅读

继续阅读入口展示最近会话：

- 故事标题
- 当前角色
- 最近段落摘要
- 更新时间
- 关键节点数量

点击后直接回到阅读器。

## 7. 创作入口

创作入口包含两类创建能力，必须在文案上区分清楚：

- 创建入戏角色：给读者自己使用，进入故事时作为“我是谁”的上下文。
- 创建故事世界：给其他读者进入，包含封面、世界设定、起点场景、故事演员和 AI 体验配置。

创作入口必须和故事探索入口分离：

- `故事`：探索所有可进入的故事，包含平台示例故事和其他用户发布或可见的故事。
- `创作`：用户控制台，包含 `我的故事` 和 `我的角色`，用于创建、查看和后续编辑自己的内容。
- `管理后台`：管理员和运营工具，不作为普通用户创作入口，不使用用户侧创作表单。

参考项目的创建入口可以抽象为底部弹层：

```text
创建

角色
故事世界
草稿
创作指南
```

MVP 只启用：

- 创建角色
- 创建故事，配置故事 ID、标题、标语、封面图、类型、世界前提、起点场景和世界规则
- 从已有角色中选择故事演员，AI 会模拟这些演员和读者对话或互动
- 选择入戏体验模式，作为作者创建故事时的核心体验开关
- 选择默认生成长度，控制读者每次继续阅读获得的正文规模
- 保存后回到故事世界列表，用户可以立即选择角色进入试玩

暂缓：

- 图片生成
- 群聊
- 作品动态
- 复杂草稿系统
- 创作者收益看板和提现
- 发布审核和积分体系

### 7.1 创建故事表单

创建故事应分成三段，避免用户一开始面对完整创作后台：

1. 基础展示
   - 故事 ID
   - 标题
   - 标语
   - 类型
   - 封面图 URL
   - 可见性：仅自己可见、公开到故事探索

2. 世界入口
   - 世界前提
   - 起点地点
   - 起点场景描述
   - 世界规则

3. 故事演员
   - 从当前用户自己的角色库选择一个或多个角色。
   - 创建故事时复制为故事内角色快照。
   - 读者输入动作或对话后，AI 按这些演员的性格、目标和约束做出回应。
   - MVP 先复用角色基础人设；后续再开放故事内重设项，例如故事身份、与读者关系、秘密、不可透露信息、当前目标和行为边界。

4. AI 体验
   - 入戏体验模式
   - 默认生成长度
   - AI 自由度

创建完成后默认仅自己可见，出现在 `创作 -> 我的故事`。只有设置为公开的故事才进入 `故事` 探索入口。MVP 不处理正式发布、审核、积分和收益，只验证用户能否顺畅完成“创建故事 -> 公开或试玩 -> 选择角色 -> 进入故事 -> 入戏互动”的闭环。

我的故事管理在 MVP 阶段提供展开式编辑：

- 列表展示标题、标语、类型。
- 展开后可编辑故事展示信息、可见性、世界前提、起点场景、世界规则、入戏体验模式、默认生成长度和 AI 自由度。
- 展开后可选择一个入戏身份试玩故事，直接进入阅读器检查开场体验。已经试玩过的故事给出两个按钮：`回到上次试玩` 回到那份进度，`从开场重新试玩` 才新建一份。
- 可以删除自己创建的故事；平台示例故事和其他用户故事不可删除。
- 删除故事和角色前需要二次确认，降低移动端误触风险。
- 故事演员的故事内重设在故事工作台里：展开故事后可以逐个演员改写故事身份、与读者的关系、秘密和当前目标，这些设定只属于这个故事。

## 8. 管理后台与客户端的边界

客户端：

- 面向普通用户。
- 负责阅读、入戏、我的角色、轻量创作。

管理后台：

- 面向开发者和运营。
- 负责模型配置、Provider 验证、会话审计和运行状态观察。
- 入口是账号栏的 `管理控制台` 链接，只对 `admin` 角色出现；页面自身也按角色拦截（见 §11）。

不要把管理后台设计成创作入口。普通用户创建故事必须从客户端底部 Tab 或顶部导航的 `创作` 进入。

## 9. MVP 落地顺序

1. 更新首页为故事探索 + 继续阅读 + 创作控制台的组合入口。
2. 在创作控制台实现我的角色列表和创建表单。
3. 进入故事前增加角色选择。
4. 阅读器增加当前角色胶囊。
5. 阅读器增加常驻“入戏”按钮。
6. 将当前回合式输入收敛为入戏面板。
7. 服务端增加关键介入节点数据结构。
8. 将叙事生成从单回合推进逐步调整为段落式阅读推进。

## 10. 成功标准

- 用户可以不做选择也能顺畅阅读。
- 用户随时能明确“我是谁”。
- 用户能在关键节点或主动点击按钮后参与故事。
- AI 输出能体现用户角色设定。
- 阅读器不像普通聊天工具，也不像后台管理页面。

## 11. 角色与权限

产品里只有两种账号角色（`users.role`）：`reader` 和 `admin`。"创作者"不是独立角色——任何读者都可以创作，创作能力靠首页的 `创作` Tab 提供，不需要授权。

- 访客：未登录。除 `/login` 外的页面一律重定向到 `/login`。
- 读者（`reader`）：阅读、入戏、管理自己的角色库和故事。看不到、也进不去管理控制台。
- 管理员（`admin`）：读者的全部能力，外加 `/admin` 管理控制台。

管理员身份有三条获得路径，按适用场景排序：

1. `ADMIN_EMAILS`：逗号分隔的邮箱清单。注册时直接成为管理员；清单里的已有账号在下一次登录时自动提权。这是新装环境和已有数据库都适用的方式，不需要连数据库。
2. `PUT /api/admin/users/:userId/role`：已有管理员（或持共享 token 的自动化脚本）把角色发给别人。
3. `ADMIN_TOKEN`：共享凭证，只作为第一个管理员的引导路径和自动化用；浏览器端不使用它。

`/admin` 页面本身按账号角色拦截：未登录跳 `/login`，读者跳回首页。控制台的数据请求由服务端携带 `ADMIN_TOKEN`，与访问者无关，所以页面级校验是唯一的门。

## 12. 各类用户的完整流程

### 12.1 访客

1. 打开任意地址 → 重定向 `/login`。
2. `登录` / `注册` 两个 Tab（`/login?mode=register`）。注册需要邮箱、昵称、密码（≥8 位）。
3. 失败时错误在表单内显示，输入保留。
4. 成功 → 写入 `instory_session` Cookie（httpOnly，30 天）→ 进入首页。首页右上角的账号栏写着昵称和邮箱，所以随时能确认现在登录的是哪个账号。

### 12.2 读者：从进门到入戏

1. 首页 `故事` Tab：卡片上方有搜索（标题 / 钩子 / 类型）、类型筛选和排序（最近有人读 / 读者最多 / 按标题，默认第一项）。每张卡片显示类型、AI 自由度、入戏体验、生成长度、阅读装帧，这个故事被多少人读过、最深读到第几回合（`GET /api/stories/insights`，聚合数字，排除作者自己的试玩；没人读过就直说），以及一句长度预期：「主线 N 个节点 · 每段约 X 字 · 约 M 分钟起」，没有预设节点的故事就说长度由读者和 AI 一起决定。一个公开故事都没有时，这里给空态并指向 `创作`，不是留一片空白；筛不出结果是另一种空态，只提示换条件。
2. 没读过的故事：在卡片上选「入戏身份」（默认角色，或自己角色库里的角色）→ `进入故事`，创建会话并跳转 `/story/:sessionId`。
3. 读过的故事：卡片变成 `继续故事`，直接回到原会话；`继续` Tab 也列出所有阅读进度，作者自己故事的试玩会话带一枚「试玩」标签（试玩同样计入当日配额）。
4. 阅读器里：
   - `继续阅读` 按当前身份自然推进下一小节，正文流式逐字上屏，可中途 `停止生成`。
   - `入戏行动` 展开行动面板：快捷动作、本幕建议（带风险标签）、自由输入（≤2000 字，⌘/Ctrl+Enter 提交）。
   - 工具坞：`状态`（场景、位置、情绪、线索）、`记忆`（存档时间线、`恢复此存档`、`重置会话`）、`行动`、`版式`（字号、行距、行宽；存在本机 `localStorage`，跨故事沿用，只影响自己）、`沉浸阅读`（隐藏信息栏）。
   - 顶栏：`← 书架` 回首页、故事标题、当前身份、今日剩余配额（悬停能看到配额几点恢复，用完时直接写在标签上）。
   - 换地点时正文出现场景分隔；只加载了一个窗口的回合，更早的用 `载入更早的回合` 取回。
5. 配额用尽或触发限流时，错误显示在行动面板或正文下方：限流给出可重试的秒数，配额用尽给出按本机时区换算的恢复时刻。

### 12.3 读者作为创作者：从建角色到试玩

1. 首页 `创作` Tab → 二级 `角色库` / `故事工作台`。
2. `角色库` → `创建入戏角色`：名称、性别、性格、头像 URL、身份背景。这些字段是 AI 写"你"的依据，不是个人资料；角色一律只有自己能看见，所以没有可见性选项。
3. `故事工作台` → `创建新故事`，四段一次提交：
   - 展示信息：故事 ID（小写字母数字与连字符，≥3 位）、标题、类型、一句话钩子、封面 URL、可见性
   - 世界入口：世界前提、起点地点、起点场景、世界规则（一行一条）
   - 故事演员：从自己的角色库勾选
   - AI 体验：入戏体验、生成长度、AI 自由度、阅读装帧
4. 保存后故事出现在 `我的故事`（默认仅自己可见）。展开可编辑全部字段、试玩（首次是 `试玩故事`，之后是 `回到上次试玩` 与 `从开场重新试玩`）、`删除故事`（二次确认）。
5. 设为 `公开` 后才进入 `故事` 探索入口，其他读者可见。
6. 展开的故事下方是 `故事演员`：勾进来的角色在这里做故事内重设——故事身份、与读者的关系、秘密（读者看不到）、当前目标、性格、不能做的事。改这里只影响这个故事，角色库里的原角色不动。
7. 再下方是 `剧情锚点`：逐条写下必须发生、可以发生、禁止提前发生、可作为结局的事件（`PUT /api/me/stories/:storyId/anchors`，整组替换）。这是作者对 AI 的硬约束，没有锚点时 AI 只受世界规则约束。
8. `我的故事` 每一行下面写着这个故事被读到了什么程度：读者数、进度数、总回合、最深回合、最近阅读日期（`GET /api/me/story-insights`）。只有聚合数字，不含读者身份和输入；作者自己的试玩不计入，所以"还没有人读过"是真的没有。

### 12.4 管理员：从提权到运维

1. 按 §11 拿到 `admin` 角色（本地开发最省事的是 `ADMIN_EMAILS`）。
2. 首页账号栏出现 `管理控制台` 链接 → `/admin`。
3. 控制台分区：模型配置与 `验证当前 Provider`、用量（全站当日总量 + 按故事一张表：读者数、作者试玩、成功/失败、Token、预估成本；「读者数」不含作者本人，作者试玩单独一列，两者相加才是这个故事今天的全部生成）、账号（列出最近注册的账号与状态，逐行发放或收回管理员、`吊销登录` 结束全部会话、`停用账号` / `恢复账号`；当前登录的账号三个动作都不给自己用）、审核队列（`确认违规` / `确认违规并下架故事` / `驳回`，下架把故事设为仅自己可见并把处置写进事件）、故事基础配置（含阅读装帧）、会话列表。
4. 控制台顶栏也有账号栏：写着当前登录的昵称与邮箱，并带 `退出登录`；`客户端` 链接回到读者侧。另有 `操作记录` 分区：下架故事、吊销登录、发放或收回管理员都会留一行（谁、对什么、什么时候、说明），只追加，控制台改不了也清不掉。
5. 管理控制台不是创作入口：普通用户建故事只走 `创作` Tab，两侧不共用表单。

## 13. 与设计基线的差距（待补齐）

按当前判断的优先级，尚未做到的部分：

- 六种介入节点里，`路线出现分歧` 和 `NPC 向用户发问` 只有模型能识别：它们只存在于正文里，状态读不出来。模型不给，这两种就不会出现。

已补齐（保留记录，便于回看判断依据）：

- 卡片说得出这故事有多长：「主线 N 个节点 · 每段约 X 字 · 约 M 分钟起」，两个数字都是已知事实——作者标为必经或可作为结局的锚点条数，以及那档篇幅真正写进提示词的字数。写「起」是因为一个节点读者可能来回好几段，这是下限而不是估算。没有预设节点的故事不编数字。给出去的只有计数，锚点标题与说明仍然只在作者视图里。


- `探索故事` 有了搜索、类型筛选与排序（最近有人读 / 读者最多 / 按标题），默认按最近有人读。此前只按故事 ID 字母序，第一屏之后的故事等于不存在；读者数和最近阅读时间明明已经算出来印在卡片上，却没有一处用它排序。筛不出结果时给的是「没有符合条件的故事」和 `清空筛选`，而不是「这里还没有公开的故事」——后者会把一个打错关键词的人劝去创作。


- 配额说得出什么时候恢复：`TurnQuota` 带上 `resetsAt`（下一个 UTC 零点），界面按本机时区渲染——平时挂在配额标签的 `title` 上，配额用完时直接写进标签和错误提示。此前只说「明天再来」，而重置按 UTC 日切，东八区的「明天」其实是当天早上 8 点，说法本身就是错的。


- `退出登录` 真的退得出去：开发模式下的匿名兜底不再被当成登录身份（`GET /api/auth/me` 对兜底回 401）。此前无会话的调用会被认成种子读者「本地读者」，于是登出清掉 Cookie、跳到 `/login`，`/login` 一问"谁在登录"又得到那个种子读者、把人弹回首页——按钮看着完全没反应。同一个毛病还让任何匿名访客直接看到别人的工作台。管理控制台也补上了账号栏：写明当前账号，并且能直接退出。

- 表单被拒时说得出原因：重复的故事 ID 会显示「故事 ID「x」已经被占用，换一个再试。」，字段校验失败会列出出错的字段名（用表单里的中文标签，不是 Zod 原文），故事 ID 的规则写在标签上。此前服务端写好的原因和字段列表都被客户端读出来又丢掉，作者只看到一句「创建故事失败」，无从下手。


- 一次推进只花一次生成：只有在流还没开起来时（模型不支持流式、传输层拒绝）才回落到非流式端点；流开起来之后的失败——模型报错、审核拦下、连接中断——直接报给读者。此前任何一种失败都会回落，于是同一次动作调两次模型、花两份 token 和两份突发额度，而审核拦下的那一段回落后照样会被拦下。

- `停止生成` 是真的停下：读者中断后，服务端发现连接已断就不再记成功用量、不把这一段写进正文，Provider 也会取消上游响应体，模型不再往一条没人读的流里生成。此前服务端对中断毫不知情——它把生成跑完、记一次成功、把整段落库，于是界面说"已停止"、配额少一次、下次打开还会看到那一段。中断仍记一条失败用量：模型被调用过，钱花了，管理台不该看不见。

- 读者拿到的故事详情不再包含作者写给模型的部分：`GET /api/stories/:id` 只对故事作者返回完整内容，其他人（包括正在读的读者和未登录调用者）拿到的是世界设定加"演员姓名与故事身份"，秘密、目标、禁止项和全部剧情锚点都不在其中。此前知道一个公开故事的 ID 就能取到每个演员的秘密和整份大纲——含 `禁止提前发生` 与 `可作为结局` 的条目，等于开读前先拿到结局。锚点是整块不返回，不是返回空数组：空数组会让人以为这个故事没有锚点。

- 创建与保存都会在按钮旁给出成功或失败的回执；创建失败时把填过的内容原样送回，不再丢稿。
- 有了 `error.tsx` 和 `not-found.tsx`：失效的阅读进度按 404 呈现，其他异常给出重试和回书架两个出口。
- 破坏性操作的确认标准统一了：`重置会话` 和 `恢复此存档` 与删除故事/角色一样会先问一次，并说明后果不可撤销。
- `继续` 卡片可以删除这段阅读进度（`DELETE /api/sessions/:id`，按 owner 校验，回合与存档一并删除）。
- 今日配额随会话读取一起返回，进门就能看到，不必先花掉一次才知道还剩多少；`GET /api/me/quota` 让首页那张卡也说同一个数字（「你今天还剩 N 次」＋一枚「今日剩余」），所以决定要不要开一段之前就知道自己还剩多少。
- `继续` 卡片上的题材、篇幅、共创方式都取自真实故事配置，没有兜底值：服务端只返回故事仍然存在的会话。
- 保存已有故事/角色失败时，表单留在这一次改过的内容上，不再被服务端旧值盖回去。
- 故事工作台的试玩区分了两件事：`回到上次试玩` 直接回到那份进度，`从开场重新试玩` 才新建一份；不再每次点按都堆一张进度卡。
- 故事演员可以在故事内重设：故事身份、与读者的关系、秘密、当前目标、性格、不能做的事，都随故事保存（`PUT /api/me/stories/:storyId/characters/:characterId`），不会回写角色库。秘密只进提示词，AI 被要求只能暗示、不能直说。
- 关键介入节点（§5.3）落到了数据上：每个回合带一个 `intervention`（`kind` + 一句故事口吻的提示），随 `session_turns.intervention` 存库，刷新后仍在。界面把它作为低打扰标记显示在那一段正文下面，只有最新一段带 `入戏参与`；旧节点保留标签、不再可点。与设计稿的一处偏差：提示里没有第二个 `继续阅读` 按钮——正文下方常驻栏已经有一个，重复放一遍只是噪音，继续读下去本来就是默认答案。
- 节点不依赖模型的自觉：模型不标时，服务端按这一段真实改变的状态补一个（恐惧/警觉骤升 → 危机，关系值变动 → 关系变化，新线索 → 发现线索，场景切换 → 剧情转折），只对 `继续阅读` 推进的段落生效——读者刚自己行动过的那一段，本来就是他的回合。
- 剧情锚点从"只有种子故事有"变成作者可编辑：`创作 → 故事工作台 → 展开故事 → 剧情锚点`，整组替换保存。此前 `story_anchors` 只在种子数据里有行，用户自建的故事永远是空的，而锚点是进提示词的硬约束——作者能配的最强控制手段一直拿不到。
- 作者能看到自己的故事有没有人读：每行给出读者数、进度数、总回合、最深回合和最近阅读日期。只有聚合数字，不含读者身份和输入；作者自己的试玩被排除在外，否则每个没人读的故事都会显示成有读者。
- `仅自己可见` 真的只有自己可见：`GET /api/stories/:id` 和 `POST /api/stories/:id/sessions` 都要求故事公开或属于调用者，否则一律 404（不是 403，免得确认这个 ID 存在）。此前知道 ID 就能读到整个世界观、演员和锚点，也能直接开读。已经在读的人不受影响——手里有会话的读者仍可读取故事标题与装帧，作者把故事下架不会把他踢出正在读的一段。
- 故事被删除后，`继续` 里留下一张墓碑卡片：写着当初打开时记下的故事名、读到第几回合、最后读到的那一段，说明"作者已删除这个故事"，只能移除卡片。会话现在自己记着故事名（迁移 9 快照到 `reader_sessions.story_title`），所以标题不依赖那个已经不存在的故事。此前这张卡片会一声不响地从书架上消失，看起来像阅读丢了而不是故事没了。
- 探索卡片写出这个故事被多少人读过、最深读到第几回合，读者第一次能在开读前判断值不值得开始。与创作者视图共用同一份聚合，按每个故事各自的作者排除试玩——公开书架上的故事作者各不相同，所以排除是逐故事的，不是一个 ID 排到底。
